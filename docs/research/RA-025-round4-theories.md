## 3. The round-4 corpus discovery — the gaudi-cookbook GLM-5.3 decode playbook (GaudiGrimoire, tier D, thediymaker/gaudi-cookbook @ 15402637)

The corpus contains a complete, measured, production-validated playbook for the EXACT decode problem we are solving — GLM-5.3 (744B MoE, 256 routed experts top-8, MLA+DSA, MTP k=1, TP8+EP, 8× Gaudi 2, Gaudi SW 1.24.1, vllm-gaudi) — with 8-rank traces, per-route kernel costs, layout experiments, and the full lever set. Our model (GLM-5.3-Flash: 288 experts top-8, hidden 4096, 42 MoE layers, block-FP8) is the same architecture class, ~40% smaller per layer. Key measured facts:

1. **The decode-step anatomy (moe-decode-step.md, G27):** one stream, ~2.8K context, step 39.0-39.4 ms: **expert kernels on the SLOWEST EP rank 19.5 ms (mean rank 9.6 ms — the EP imbalance is 9.9 ms of the step)**; MLA attention 6.9 ms; MoE outside the kernels (gate/shared/router/combine) 3.8 ms; 162 all-reduces × ~20 µs = 3.4 ms; host-with-device-idle ~5.5 ms (the host runs ahead during the forward — critical only at the step boundary). "A lazy-mode collective ends a recipe, so each layer replays as two recipes and two all-reduces: 322 graph launches per step at ~74 µs host time each." At 4 streams: slowest-rank expert 50.7 vs mean 30.7 ms. **The slowest rank, not the mean rank, is the critical path — rank-0-only tracing hides the straggler.**
2. **The EP imbalance is balls-in-bins statistics, not a hot rank (G27):** 16 routes (verify + draft, top-8) into 8 ranks: busiest 4.45 vs mean 2.0; a random placement matches the contiguous one (no hot expert); two thirds of the gap remains under uniform routing (irremovable); the MTP verify/draft pair shares 2.4 of 8 experts (0.25 if independent) — worth ~1.0 ms, what a fitted placement recovers. **The EP4×TP2 layout (4 groups of 2 ranks, 64 experts/group, each rank half the intermediate): expert kernels 18.4-19.1 → 14.0-14.4 ms; step 35.4-36.3 → 31.3-31.4; decode 57.13 → 63.58 tok/s (+11%, v7 kernels) / 66.41 → 69.58 (+5%, v8). Per-route kernel cost: 47 µs at full width, 25 at half, 17.7 at quarter (1 card) — each route pays a fixed part (input staging, scale loads) that does not shrink.** Output NOT bit-identical (the split down-projection's bf16 partial sums) — quality gates held (GSM8K 49/50 same-answer 50/50, needles, top-1 0.988).
3. **The step-boundary levers (G27):** router fast path ~1.7 ms (the grouped top-k's group stage selects every expert when n_group=1/topk_group=1 yet costs ~25 µs/layer incl. a 12.9 µs DMA broadcast for the mask expand → go straight to the biased top-k); early draft + device-side rejection ~2 ms (the stock step end: target forward → rejection sampler → copy sampled tokens to host → build draft indices on host → enqueue draft, with the device idling 1.5 ms; computing the indices on device — last accepted row = 2i + accepted − 1 — plus moving the rejection walk to device with the SAME random draws (host float64 uniform rounded up to the next float32, so the float32 comparison equals the float64 one) removes the sync; 0 mismatches vs stock in 7,000 steps/rank). **These are exactly our Q18 levers (GLM_ROUTER_FAST / GLM_EARLY_DRAFT / GLM_SPEC_DEVICE_REJECT) — independently converged, the mechanisms and the ~3.7 ms value cross-validated.**
4. **The MXFP4 MoE decode kernels (mxfp4-moe.md, G28):** the stock MoE op lowers to a `cast_packed_mxfp4_to_bf16` TPC node per touched expert (writes 4× the packed bytes as bf16) + tiny MME GEMMs + DMAs — at batch 4: 124,000 cast calls (47.6 ms of TPC in a 97 ms step) + 33,000 GEMMs + 49,000 DMAs; the cast path moves only 0.2-0.5 TB/s of the 2.2 TB/s HBM. The custom TPC kernels (2 launches/layer + 1 small host transpose): **unpack in registers** (512-value chunks: 256-byte load → nibble split → E2M1→bf16 LUT → per-lane bf16 scale (exact) → fp32 accumulate), **routing in the kernel** (a scalar counting-sort by local expert; routes to other EP ranks cost nothing; each TPC owns a fixed output-row slice and walks its local routes — the work split is routing-independent), **software pipelining** (the last chunk pair of a pass issues the loads of the next pass, possibly a different expert), fused fp32 epilogues (SwiGLU in fp32, per-token fp32 sums). Per-MoE-call speedups (32 local experts): 1 tok 4.8×, 4 tok 8.1×, 8 tok 10×, 16 tok 5.6×, 32 tok 3.6× — "**the kernel costs about 30 µs per local route at any token count; the stock op costs about 250-300 µs per touched expert at small counts but amortises the unpack when several routes share an expert**." ### RA-030 (decode) — The stock-op MoE chunk hints: VLLM_MOE_CHUNK=256 + VLLM_MOE_TOKEN_BOUNDARY=2048

**ID:** RA-030 (round 4) · **Complexity:** LOW (2 env vars, no code) · **Status:** **REFUTED FOR DECODE (2026-11-11, same-day correction — tier B vendor code + project measurement); retained as a prefill chunk knob (adjacent to RA-033) and as a zero-cost confirmation arm in the first boot family**

**The correction (why the original "2-6 ms" expectation does not hold on our stack):**

The vendor chunking code (tier B: `gaudi-pytorch-bridge` @ 5176b1b2 — the SAME commit as our deployed venv — `hpu_ops/backend/mixture_of_experts_gen.cpp`, l.120-175):

```cpp
DimT calculate_num_chunks(num_tokens, experts_per_token, num_experts, device_threshold, chunk_size) {
  if (num_tokens <= device_threshold) {          // device_threshold = 256 on Gaudi2
    return std::min(experts_per_token * num_tokens, num_experts);   // chunk_size UNUSED
  } else {
    return num_experts * (ceil_div(experts_per_token * num_tokens, num_experts * chunk_size) + 1);
  }
}
```

For EVERY call with `num_tokens ≤ 256` (ALL our decode calls: bs=1 k=1 = 2 rows, @16 k=1 = 32 rows, even ns32 = 64), `num_chunks = min(8 × num_tokens, 36 local experts)` is **independent of the `chunk_size` argument**. The auto path (chunk_size=0, the current default) computes, for bs=1 k=1: `num_chunks = min(16, 36) = 16`, then `calculate_chunk_size` → `num_chunks/num_experts = 0 ≤ split_factor(8)` → chunk_size = 256 (the minCS floor) — **the identical (256, 16) geometry that VLLM_MOE_CHUNK=256 would set explicitly.** The `fp8_fused_weights`/`fp8_fused_weights_dynamic` variants (OUR path — `MoeFP8Matmul.forward`, `ops.py` l.1358-1390, verified on the server) route through the same `MixtureOfExpertsFwdSizes` (`MixtureOfExpertsFwdFp8Shapes`, l.~230: same `num_experts = weight-list size (36 local)`, same `chunk_size = last op arg`).

The measured stock decode MoE (15.5 ms/step = 38.1 GB/step = 36 local experts × 25.2 MB × 42 layers, the rev-1 byte model verified to <1% against the measured 39.1 t/s) independently confirms the consequence: **the kernel's per-expert weight DMAs cover ALL 36 local experts per call regardless of chunking** — the per-slot chunk structure (16 chunks at bs=1) organizes the activation GEMMs, not the weight loads. "Skip expert slots no token routes to" therefore cannot reduce the decode weight traffic on this op generation, and the cookbook's "1.6× to 2.2× faster per call at 2 to 8 tokens" (MiniMax-M3, a different model/op generation) is not reproducible from this knob at 2-8 tokens here — at those counts the geometry is chunk_size-invariant by the code above.

**What the env vars DO change:** only calls with `num_tokens > 256` — i.e., the prefill chunks (and the >2,048-row band where our boundary=2048 leaves the default 256). That is the RA-033 prefill knob, deferred per the owner directive.

**Retained use (zero cost):** keep the chunk-hints arm in the first boot family's A/B as a CONFIRMATION of this code reading (expected: 0% decode delta; a non-zero delta would falsify the reading and re-open the question — worth the one arm). The decode A/B of the first boot family is now effectively **RA-032 (the lazy collectives) + RA-031 (the recipe cache/pin)** — the two real zero-code items.
