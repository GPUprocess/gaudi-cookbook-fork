### 0.3 The central tension this round resolves

The agent has said two things that appear contradictory:

- `9e6a1b5`: the replay floor (25-45 ms) is "the platform floor (the hard)" — "this caps the k=1 iteration at ~50-60 ms REGARDLESS of the host optimization"; the corrected @16 ceiling 450-500 t/s is "the platform-constrained ceiling".
- `88a6a74`: "THE STEP IS LAUNCH-BOUND AT THE RECIPE LEVEL: **the node count IS the device time**; THE OPTIMIZATION PROGRAM IS RECIPE-LEVEL FUSION ... the Synapse fuser configuration is the lever" — plus `380303f` staging the graph_editor "for the node-count reduction program".

These are reconcilable only if the replay floor is (at least partly) the **device execution of the node-bound recipe** (not a fixed runtime constant). The GaudiGrimoire cost model (§1.3) says the truth is in between: a raw node-count census is NOT a valid cost model (metadata nodes are free on the device; the 1-3 us integer TPC nodes dominate; rank by **engine x count x mean duration**), but the MoE region's node classes (the batch_gemm MME nodes + the dequant-class TPC nodes + the moe_multiplexer TPC nodes) are exactly the classes that carry per-node cost, and the per-launch intercept law (the g2-opt-manual §4.2.10 measurement: `a(us) = 0.6706 + 8.8911 ns x bundles`, R^2 = 0.9766) gives the per-node overhead a measured magnitude of 1-3 us for small kernels — consistent with the agent's 1.3 us/node effective value.

**RA-038-A is the program that attacks the "hard floor" via per-node-class cost attribution + targeted node collapse, with a graph_editor ablation design (T2, §3) that decisively measures how much of the 25-45 ms is node-class-removable.** If the ablation shows the floor is mostly node-class-removable, the 450-500 @16 ceiling opens toward 700-900 (decode-only); if it shows the floor is a fixed runtime cost, the ceiling stands and the deep-MTP value is bounded to the bs=1 latency mode. Either way the ablation is the highest-value experiment on the board — it re-ranks every other lever.

## 1. Proposal RA-038-A: the recipe-level node-collapse program (the master lever)

### 1.1 Executive summary

The decode step is launch-bound at the recipe level: ~20.5-26.4k nodes execute in 25-45 ms (bs=1) / 27.3 ms drain (@16), of which the MoE region is 87-89% of the nodes. The node classes are known from the captured trace (batch_gemm x1,496, moe_multiplexer x1,002, dequant-class x~2,536, non-MoE x~2,300-3,300). The corpus cost model (g2-opt-manual, the vendor bridge source) says the per-node cost is engine-dependent (1-3 us for small TPC nodes, the MME GEMM work for batch_gemm, free for metadata), that one compiled recipe contains all three engines, and that the per-launch host intercept scales with the recipe's bundle count. The program: **(a)** attribute the 25-45 ms to node classes by ablation (the graph_editor: disable a class, measure the [LAUNCH] stamp delta + the MFU BW delta + the t/s); **(b)** collapse the highest-cost classes with targeted fusion — the grouped-MoE GEMM (the 1,496+1,002 MoE dispatch nodes → ~42-150), the fused norm chains (the 40x RMSNorm chains, the 1Cat `add_rmsnorm` pattern — a verified -1 launch / -393 KB win in the corpus), the fused _accept_grid (the 25-30 sampler ops → 1 kernel), the fuser's cast removal (the residual cast_f32_to_bf16 x760); **(c)** re-gate numerics per arm (the R003 knife-edge applies to every structural change of the decode residual stream). Expected: the @16 drain 27.3 → 12-22 ms and the bs=1 replay 44 → 20-36 ms (conservative to aggressive band; the ablation selects the corner). This is the single lever that cuts the floor for everything: bs=1, @16, every k, both HPU counts.

### 1.3 The corpus cost model (what the replay floor is made of)

**Hardware (g2-opt-manual, MEASURED on Gaudi 2, facts only):** 24 TPC engines (elementwise/reduce/gather/casts/softmax/custom kernels), 4 MME engines (matmul only; 2 cores each = 8 cores — the "24 MME" figure is refuted in the corpus), 8 DMA tids (5 HBM<->SRAM lanes, one transfer per lane at a time). 96 GiB HBM, 48 MiB SRAM (one shared pool, compiler-managed, no L1/L2 — "reuse must be engineered"). Bandwidth is size-dependent: TPC stream ~2,147 GB/s at >=134 MB; DMA ~1,776 GB/s at 16-64 MB, ~2,025 at >=256 MB (nominal 2,450). **Below ~16 MB, small-tile GEMV work loses bandwidth sharply — "keep decode weight tiles >= ~16 MB"** (each GLM expert is 25.2 MB — above the cliff; the routed-only reads stay above it).

**Per-node cost:** the per-launch intercept is a bundle law, sublinear: `a(us) = 0.6706 + 8.8911 ns x bundles` (R^2 = 0.9766 over 65/71 arms; `a`/bundle falls from 15.7 ns at 64 bundles to 8.6 ns at 2,029 bundles). A small TPC node (tens of bundles) costs ~1-3 us of device execution — this is the "1-3 us integer nodes dominate" the dead-ends list names, and it matches the agent's 1.3 us/node effective average. The MME cost model is accurate to 0.5% (1650 MHz, 262,144 FLOP/cycle → 432.5 TFLOP/s vs measured 430-432.7) — the batch_gemm node costs are the real GEMM work, predictable. The TPC cost-model field (`tpc_tpc_cycles`) is gated (`DUMP_TPC_COST_MODEL_DATA=1` + `ENABLE_EXPERIMENTAL_FLAGS=1`, and the kernel-side half is unsatisfiable on this compiler — `tpc-clang` 2.7.33 has no `--kernel-cost` flag) — so TPC node durations must come from the ablation, not the dumps.

**Markers:** only the TPC marker (`TPC_SPU_START_TO_SPU_HALT`) is a true start→halt span; the MME marker self-overlaps ~4x and the DMA marker ~14.5x — any raw marker-duration figure for MME/DMA is a marker figure, not an occupancy figure (relevant when the agent reads the MFU metrics: the BW 328 GB/s is a hardware-counter figure, not a marker figure — it is trustworthy; a future dump-based MME figure would need the union treatment).

**The replay path (vendor source, tier B, `habana_eager/graph_exec.cpp`):** `GraphExec::LaunchRecipeTask` = `OptimizeGraph` (first call only) + `PrepareOptimizedGraphForLaunch` + `PatchDynamicTensors` (per-launch: computes the total H2D patch size, allocates one host chunk, and writes each dynamic tensor's patch values — the host work scales with the **dynamic-tensor count**, not the node count) + `LaunchRecipe` (the Synapse launch). The per-recipe host enqueue measured in the corpus harness: 37.9 us median for a single-node compiled region at the torch-bridge layer (`enqueueWithExternalEventsExt`); the raw-Synapse sheet figure of 11-15 us is unverified. With ~322 recipes/step: 3.6-12 ms of host enqueue per step — a real, recipe-count-proportional term inside the 44 ms bs=1 figure.

**The dead-ends list (g2-opt-manual TL;DR — do not re-walk):** "a node-count census as a cost model (metadata nodes are free on the device; 1-3 us integer nodes can dominate — rank by engine x count x mean duration)"; "launch/sync/recipe counts as the lever" (as a standalone program); "pre-dequantizing experts at load (HBM-blocked)" — confirmed by our 7bb417e (no room for the 79 GB BF16 copy); "re-expressing a fused kernel in native torch ops". Two consequences for this proposal: (1) the collapse targets must be chosen per node class (engine x count x duration), not by raw count; (2) the fusion must produce a real compiled op (native extension / TPC kernel / Synapse fuser output), not a torch re-expression.

**The verified fusion precedents (corpus):** (a) the manual add_rmsnorm fusion (2→1 node): -1 launch, -393 KB DRAM round-trip (g2-opt-manual, verified tag); (b) the custom kernel inside a batch_gemm bundle: workspace 2,097,408 → 256 B (verified); (c) the arena packing (65 tensors): 75 → 4 patch points, launch ~50 → 25-35 us (verified — this is the `PatchDynamicTensors` term, the dynamic-tensor count); (d) the 1Cat fork's `fuse_projection_graph` (Apache-2.0): an FX-graph rewrite that replaces the norm+quant projection chain with one native `add_rmsnorm_quant_op`, **gated per qualified shape** ("Only this decode projection has jointly qualified against its matching CGUID consumer and the independent formula") — the exact qualification pattern the R003 numerics regime requires; (e) the 1Cat fork's `deduplicate_float_casts`: removes duplicate FP32 casts at the capture boundary — the reference pattern for the Q01v2 drift class (§2.4 D1); (f) the 1Cat Synapse `tpc_fuser.cpp` patch: the compiler-side node-replacement machinery (`replaceNodes` per fused cluster) — evidence the fuser's fusion surface is real and patchable.
