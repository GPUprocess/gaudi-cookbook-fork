## 2. The two per-phase failures, mechanistically

### 2.1 PERPHASE (the attribute patch) — the flag was inert at capture time; the "Synapse recipe memory" verdict is a misattribution

The attribute patch: the runner sets `self._glm_no_tensor_cache_this_call` in `execute_model`; the patched wrapper reads it from `orig_fwd.__self__` (graphs.py:706). My round-2 audit found D1 (the `> 0` signal is true on every step) and D2 (the attribute is set on the `HpuModelRunner` but read from the `HpuModelAdapter` — no `__getattr__` proxy — so the read is always the default False). The PERPHASE results confirm D2: decode 44.1 = the cache-ON level (the RA-001 win), prefill OOM at 2,944 = the cache-ON OOM (PFG+MHC). The prefill captures were NOT cache-free — the flag never reached them.

The recorded verdict — "the cache-free prefill captures STILL OOM; the workspace is the Synapse-level recipe memory; the MEMLOG's 184-MiB tensors are the RECIPE's internal buffers, not the wrapper's cached tensors" — requires that the 2,944 capture actually ran cache-free (dry_run=True). It did not (the decode 44.1 in the same boot is the proof). The control exists: **ABCONFIG-WIN captured the same 2,944-row shape cache-free (wrap-time `GLM_TENSOR_CACHE_OFF=1`) and it worked** (5,546-7,723 t/s across the band, full KV 1280). So the tensor-cache lever is NOT refuted; it is simply untested in a per-phase form that was actually active at capture time.

The recipe-memory mechanism itself is REAL (G25, tier B + D): each compiled Synapse recipe carries a workspace (`synWorkspaceGetSize` per recipe handle, allocated from the device workspace pool; the recipe handle cache in `habana_operator.cpp`; the two-level compile — "Level 2 — Synapse graphs, compiled at launch time from (recipe × concrete shapes × bucket × shape-tensor/dynamic-bucket info)"). Whether the cache-free (dry_run) capture's recipe workspace fits is exactly what ABCONFIG-WIN already proved: it fits (the 2,944/4,096 captures succeeded and replayed). The question the PERPHASE verdict poses ("does a truly cache-free 2,944 capture OOM?") has a MEASURED answer: no — but RA-022 should re-confirm it under the per-phase configuration, because that is the one boot that discriminates the two theories cleanly (§4).

### 2.2 RA-020 (the env-var route) — the mechanism works; the signal was the D1 flaw; the capture timing made it fatal

The env-var route is the vendor's own mechanism (G20, tier B: `wrapped_hpugraph_forward` reads `PT_HPUGRAPH_DISABLE_TENSOR_CACHE` on every call, l.697; the value drives the disable_tensor_cache semantics AND the derived `dry_run`, l.699-700). The deployment (l.4273-4274) sets it per call in `execute_model` with `_is_prompt_step = scheduler_output.total_num_scheduled_tokens > 0` (l.4266) — the D1 flaw, carried over from the first patch's signal. Consequences:

1. Every non-empty execute_model step — decode included — set the env to "1" (the `scheduler.py:1065` sum includes the decode requests, each ≥1; MTP verify ≥1+k).
2. The decode shapes that are pre-warmed at `warmup_graphs` (l.5682 — the startup bucket loop, OUTSIDE execute_model, env unset → the wrap-time value, cache-ON) are fine. But the **MTP-verify shape (2N rows — the actual decode shape under MTP k=1) is captured on first use** (the warmed decode buckets are the non-verify shapes; the first 2N-row step is a serving step, where the env was "1" per point 1) → the verify entry is captured cache-OFF → sticky (the entry's mode is fixed at first capture) → every decode step replays the cache-OFF entry → 36.5-38.5.
3. The prefill >2,048 shapes: captured cache-OFF if on first use (env "1" — harmless), cache-ON if pre-warmed (env unset at warmup → OOM risk — the record does not show a ladder, so this is unverified for that boot; the RA-022 design removes the ambiguity by patching the warmup site too).

**The general lesson (applies to any per-phase state on this stack):** the capture happens at startup (`warmup_graphs` + `profile_run` + the first-use captures of the unwarmed shapes), and the capture-time value of the per-shape state is STICKY (the entry is created once, per input hash). A signal set in `execute_model` cannot control the mode of pre-warmed shapes at all, and it controls first-use shapes only if the signal is correct at that first step. The control point is the CAPTURE SITE.

## 3. The new facts from COMBINED-WIN/COMPOSE (the three-profile matrix + the draft-graph sign flip)

1. **The Q01v2 +20% is cache-DEPENDENT:** the draft graphs gain +8 t/s on cache-ON (the Q01v2 measurement, 42.4→~50) but only +5.5 on cache-OFF (37.3→42.8). The graph replay's benefit is larger when the tensor cache retains the staging buffers. Under the RA-022 full composition (decode cache-ON), the +20% is expected to compose — the bs=1 end-state with the draft graphs + T7 acceptance is ~50 t/s.
2. **The draft graphs flip sign at @16: −7%** (237.6-241.7 vs 257-259). The Q01v2 era measured the draft graphs at @16 only on the pre-Q18-lever stack (+33% vs the 126.7 base — a different regime). On the current stack the per-stream draft-graph cost exceeds the benefit at 16 streams. Candidate mechanisms: (a) the SEAM — the draft graph is a second synchronous replay boundary per step (the host blocks on the verify graph, then again on the draft graph; ~constant cost, proportionally large on the host/launch-bound step); (b) the per-row input staging (the draft's metadata/hidden inputs grow with rows). The discriminator is cheap: the draft-graph A/B at bs=1/4/8/16 on the adopted profile (one boot family) — a ~constant gap → the seam (T2's chain graph is the fix — it removes the boundary); a row-linear gap → the staging (a shared-staging fix). Either way T2 (the chain graph: the draft inside the verify graph, one replay) is the end-state fix, and its value is now quantified at two points: @16 k=1 −7% (the draft-graph cost) and @16 k=4 −38% (MTP4-T0: the 5× verify-row shapes + the eager chain ×4).
3. **The matrix is the owner's decision, and T7 is the unlock** — but RA-022 adds a fourth profile (the full composition: decode cache-ON + prefill >2,048 cache-OFF): expected 42.4 / ~257 / MET / 100% (the decode path bit-identical to the pre-ABCONFIG profile), and with the draft graphs (T7-accepted): ~50 / ~250 / MET / 97.5% (R003, source 1 — the fusion drift, mode-independent).

## 4. RA-022 — Capture-site tensor-cache control with the corrected row-count signal (the decisive one-boot experiment)

**The fix (all in the runner — no vendor patch; the env-var route is the vendor mechanism, G20):**
1. **Correct the signal** (the D1 fix): `_is_prompt_step` → the ROW-COUNT CLASS: `scheduler_output.total_num_scheduled_tokens > 2048`. The demonstrated OOM boundary is between 2,048 rows (captured fine cache-ON — the PFG+MHC 2048 bucket, the adopted profile) and 2,944 (OOM cache-ON; fine cache-OFF — ABCONFIG-WIN). The decode class is ≤ 64 rows at ns32 (2 rows/request × 32) even under MTP k=1; the ≤2,048-row prefill class was fine cache-ON. So: env "1" (cache-OFF) only for the >2,048-row steps; env "0" for everything else.
2. **Set the env at the CAPTURE SITE, not (only) in execute_model:**
   - `warmup_graphs` (hpu_model_runner.py:5682): inside the bucket loop, before each `_prepare_dummy_scenario` call — `batch_seq` is ALREADY computed there (l.5702-5705: the prompt row count). Set `os.environ["PT_HPUGRAPH_DISABLE_TENSOR_CACHE"] = "1" if (is_prompt and batch_seq > 2048) else "0"` (two lines). This makes the pre-warmed shapes capture in the correct mode regardless of serving-time state.
   - `profile_run` (hpu_model_runner.py:6529): set "1" before the dummy forward (the profile dummy is max-size = the prompt class; a cache-ON capture there would also distort the free-memory measurement that sizes the KV pool).
   - Keep the execute_model set (with the corrected signal) as the first-use safety net for the unwarmed shapes (the MTP-verify shape, the draft shapes).
3. **Revert the 3-site graphs.py attribute patch** (the inert D2 patch — the env route makes it unnecessary; the `.stock-bak` files are in the venv for the revert).
4. **Verification (the boot family):** the capture-mode log first (the wrapper runs verbose=1/log_frequency=1 — confirm per-bucket the mode: the decode buckets cached, the >2,048 prompt buckets dry-run) — this is the gate that the PERPHASE/RA-020 misreads are not repeated; then the decode bench (expected 42.4-44 — the RA-001 win), the prefill ladder (2,944 MUST pass — the ABCONFIG-WIN numbers), the @16 (expected ~257-259), the suite (expected 100% — the decode path bit-identical to the pre-ABCONFIG 100% profile; a miss is a T7 data point, not an RA-022 failure), the per-card HBM at idle (the retained graph memory — feeds RA-024).

If it OOMs with the verified cache-free mode, the recipe memory is REAL and independent of the tensor cache (contradicting ABCONFIG-WIN — in which case the difference between the two boots must be found first: the KV size, the threshold, the other envs), and RA-019 (the recipe-count/workspace reduction) or the abotsis graph implementation (RA-024) becomes the only path to the >2,048 graphs. ## 7. RA-019 update — the abotsis retirement precedent and the design constraint

The abotsis fork **tried and retired the full-mHC TPC fused kernel** (G22, tier D, their `glm5_next.py`): "The TPC mHC fused-kernel experiment was retired: its per-launch cost ate the MME win it targeted (**multi-output custom ops don't split recipes**)." This is a direct precedent against RA-019's naive design (one TPC program for the whole mhc_pre chain, multiple outputs). The DSV4.1 `control_mme` family (G19) is the working pattern: a FAMILY of single-purpose ops (control_rrms_*, control_mme_f32, the gates, sinkhorn4) — the recipe splitter can partition around them. RA-019's design constraint is now explicit: **structure the mHC-prep kernel as a family of single-output (or recipe-splittable) custom ops, not one multi-output op.** Its value proposition re-scopes with RA-022: no longer the prefill-OOM critical path (RA-022 resolves that at the config level), but (a) the cache-ON-everywhere full composition (the >2,048 graphs WITH the decode cache win — the 4-HPU HBM headroom), (b) the 2,944/4,096-bucket prefill speed (MHC-ROWS +19% is T7-adoptable → the prefill goes faster still), (c) the >8,192-token prefill band. Priority: after RA-022 + T7 (weeks-scale, unchanged).
